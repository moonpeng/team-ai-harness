# AI Coding Git 提交规范

> 约束 AI 编码工具自动生成的 Git 提交 v1.0 ｜ 2026-09-14

## 1. 准入条件

以下条件全部满足后才可提交。可在已有授权范围内补齐的检查、修复和提交信息应继续完成；仅缺少授权、需要用户决策或遇到无法自行解决的阻塞时向用户确认，不得绕过准入条件。

- **已授权** — 用户明确要求提交；遵循根目录 `AGENTS.md` 的提交授权约束，不接受其他文件中的预授权。
- **验证通过** — 通过与改动影响范围匹配的验证；代码、依赖或构建配置变更须通过受影响模块的构建与相关既有测试。纯文档变更检查内容、引用路径及适用的文档检查，不要求无关工程构建。不得跳过项目明确要求的检查或提交半成品。
- **原子性** — 一个提交只做一件事。
- **可追溯** — 能看出为什么改，且标注了 AI 参与事实。

## 2. 提交信息格式

```text
<type>(<scope>): <subject>     ← ≤72 字符，小写开头，句末无句号

<body>                         ← 写 Why，不写 What；每行 ≤100 字符

<footer>                       ← AI 溯源 trailer
```

**type**：`feat` `fix` `refactor` `perf` `style` `docs` `test` `build` `ci` `chore` `revert`，禁止自创（`update` / `wip` / `tmp`）。破坏性变更加 `!` 并在 footer 写 `BREAKING CHANGE:`。

**scope**：模块语义名（`order`），非目录路径。优先复用 `git log` 中已有的 scope；跨多模块则省略。

**subject**：祈使句现在时；语言跟随仓库历史，无历史时默认中文；禁止 AI 自称（"我"、"AI 已帮你"）和空洞描述（`fix bug`、`修改代码`）。

**body**：`fix` 类必填（现象 + 根因）；有非显而易见取舍、涉及兼容性/数据迁移时必填。纯格式或错别字修改可省。

**footer**：

| Trailer                     	| 必填         	| 说明                 	|
|-----------------------------	|--------------	|----------------------	|
| `Assisted-by: Claude Code ` 	| ✅            	| AI 工具名            	|
| `Model: claude-sonnet-4.5`  	| ✅            	| 实际生成所用模型标识 	|
| `BREAKING CHANGE:`          	| 破坏性变更时 	| 影响面与迁移方式     	|

`Model` 取值必须是工具实际暴露的模型标识，不得臆测或留空；工具未提供时写 `Model: unknown`，不要编造。记录模型是为了在出现问题时能区分是模型能力边界、提示词缺陷还是审查疏漏。

不要用 `Co-authored-by` 标注 AI — 该字段表示真实人类作者，混用会污染贡献者统计与 `CODEOWNERS` 判定。

## 3. 粒度

**必须拆分**：功能 + 无关格式化；缺陷修复 + 顺手重构；源码 + 无关依赖升级；多个独立功能点。拆分时用 `git add <文件>` 分批暂存。
**不可拆分**：源码 + 对应测试；迁移脚本 + 使用它的代码；重命名 + 全部引用点；依赖升级 + 必需的源码适配。拆开会产生无法运行的中间态。
**禁止提交**：`wip`/临时保存；空提交；编译或测试失败的提交；密钥、token、`.env`、证书；`node_modules`、构建产物、IDE 配置。

## 4. 执行流程

```text
git status → git diff → git log -10（对齐风格）
git add <明确文件> → git diff --staged
→ 按 4.4 判断是否触发 OCR；不触发则跳过，触发则按该节完成审查与确认
→ git commit（heredoc）→ git status
```

**禁止**：`git add -A` / `git add .`（易纳入密钥与大文件）。

### 4.1 受限操作（需用户逐次显式指令）

`--no-verify` `--no-gpg-sign` ｜ `--amend` ｜ `push --force` ｜ `reset --hard` `checkout .` `clean -f` ｜ `push` ｜ 改 `git config` ｜ 删分支 ｜ `rebase -i`

一次授权不代表永久授权。

### 4.2 hook 失败

读输出定位根因 → 修代码 → 重新 `add` → 创建**新提交**（不是 amend，hook 失败时提交并未发生，amend 会破坏上一个提交）。三次仍失败则停止并说明阻塞点，不得绕过。

### 4.3 异常状态

遇到来源不明的改动或陌生分支，先确认状态。只提交本次用户授权范围内的改动；同一文件混有无关改动时按块暂存，无法可靠区分时询问用户。不 stash、不删除、不覆盖用户改动。

每次成功提交后，仅当仓库根目录已有 `.codegraph/` 时检查本机是否安装 `codegraph`；已有索引且工具已安装时执行 `codegraph sync` 并检查结果，否则说明并跳过，不自动安装或初始化索引。

## 5. 示例

```text
build(common): 建立公共组件聚合模块与版本管理
以 core、all 和 bom 分离基础能力、统一依赖入口及版本管理，统一 Java 8 构建配置。

Assisted-by: Codex
Model: unknown
```

| ❌                                	| 问题                                 	| 说明                 	|
|----------------------------------	|--------------------------------------	|----------------------	|
| `update code`                    	| 无 type，零信息量                    	| AI 工具名            	|
| `fix(bug): 修复bug`              	| scope 无意义，subject 重复 type      	| 实际生成所用模型标识 	|
| `feat: 新增接口并优化了部分代码` 	| 多意图混杂                           	| 影响面与迁移方式     	|
| `Co-authored-by: Qoder `         	| 误用人类共同作者字段                 	|                      	|
| 只有 `Assisted-by`，无 `Model`   	| 无法定位是哪个模型产出，失去审计价值 	|                      	|
| `fix: 修改 A.java 第 10 行`      	| 复述 diff，未说明原因                	|                      	|

## 6. 提交前自检

```text
[ ] 已获授权，已看 git status / git diff 确认改动与文件范围
[ ] 已按 4.4 判断 OCR 触发条件：不触发时已说明跳过；触发时，工具未安装且已说明跳过，或已报告审查结果/阻塞并取得用户对当前拟提交内容的明确确认
[ ] 已看 git log 对齐风格与 scope 用词
[ ] 提交原子；header ≤72 字符；type 合法；subject 有信息量
[ ] fix 类已写明根因
[ ] 已附 Assisted-by 与 Model（取自工具实际值，未编造）
[ ] 有关联工作项时已附 Workitem
[ ] 无密钥、构建产物、依赖目录
[ ] 未执行未经用户逐次明确授权的受限操作；未擅自 push
```
