# MyBatis-Plus 持久化规范

适用场景：新增、修改或审查 Mapper、XML、Wrapper、实体持久化映射、查询写入行为或事务边界。

仅约束新增代码及本次实质修改的部分，不顺带整改无关存量代码；明确要求规范化整改时按指定范围执行。

## 基础约定

- 业务 Mapper 放在 `mapper.<业务域>`；对象命名与层间边界由 [架构规范](architecture.md) 定义。
- 实体 CRUD 业务 Mapper 必须标注 MyBatis 的 `@Mapper`，并继承 `BaseMapperPlus<Entity类型>`，不得直接继承原生 `BaseMapper`；通用基接口不受此限制。
- 沿用项目现有依赖版本、基础类和插件配置，不为局部数据访问需求擅自升级框架或引入新的通用封装。

## SQL 实现选择

- 简单单表 CRUD 优先使用 MyBatis-Plus API；多表关联、复杂聚合或难以清晰表达的查询使用 XML。
- SQL 只允许 MyBatis-Plus API 与 XML 两种载体；不得使用注解 SQL，也不得在 Controller 或 Service 中编写原始 SQL。
- 同一数据访问操作只保留一种实现；已有 XML SQL 时，不再用 Wrapper 重复实现相同逻辑。
- 使用 Wrapper 时优先选择 Lambda Wrapper，以实体属性引用表达字段；复杂 SQL 不通过字符串片段强行塞入 Wrapper。

## Mapper 与 XML

- 需要自定义 SQL 时，一个业务 Mapper 对应一个 XML，放在 `resources/mapper/<业务域>/`；仅使用 MyBatis-Plus API 时不创建空 XML。
- `mapper-locations` 全局统一为 `classpath*:/mapper/**/*Mapper.xml`，不得为单个模块另配扫描路径。
- XML 的 namespace 必须对应 Mapper 完整类名，语句 id 与接口方法一致；多个自定义参数使用 `@Param` 明确命名，并与 XML 引用保持一致。
- XML 禁止 `select *`，必须显式列出字段或复用 `<sql>` 片段；多表查询必须定义 `resultMap`，重名列使用明确别名。
- 常规持久化结果使用 Entity；多表或聚合投影按需使用内部 DTO，不为承载查询结果向 Entity 添加无关字段，也不直接返回接口 Response。

## 查询条件与安全

- 查询值使用参数绑定；XML 使用 `#{}`，不得通过 `${}` 或字符串拼接接收客户端查询值。
- 动态排序、列名等不能作为普通值绑定的内容，必须由服务端白名单映射；不得将客户端字符串直接传入 SQL 片段或 Wrapper 的原始 SQL 接口。
- 明确可选条件和空集合的含义；不得因跳过空的 `IN` 条件或缺失条件而意外扩大查询、更新或删除范围。
- 修改数据访问时，保留该业务适用的逻辑删除、租户隔离和数据权限条件；不得假定自定义 XML 已自动具备这些限制。业务确需改变数据范围时，明确说明并验证。
- 列表查询按接口契约控制数据范围；分页沿用现有分页配置，并指定稳定排序，不另建重复的分页机制。

## 写入与事务

- 新增、修改只写入本次操作允许变更的字段；Entity 转换白名单与实际 SQL、Wrapper 更新字段必须一致，不能将未映射字段以 null 意外写回。
- 普通修改不得覆盖创建信息、删除标识或非本次操作可修改的状态；审计操作人来自服务端可信身份，不直接采信客户端值。
- 主键策略、逻辑删除、字段填充和数据库默认值沿用既有设计，不擅自新增注解或改变字段生成责任。
- 明确更新中的 null 表示“清空”还是“不修改”，选择与业务语义一致的更新方式，不依赖未经确认的默认更新策略。
- 更新、删除必须具有明确的目标范围；不得因动态条件缺失而执行全表操作。全量操作仅在明确业务需求下实现。
- 需要原子性的多步写入在 Service 层管理事务；不在 Mapper 层编排业务事务，不吞掉异常并返回成功。
- 根据业务语义处理受影响行数，不一律将零行视为成功或不存在；幂等操作应区分“数据未变化”和“目标不存在”。

表、字段、索引或 DDL 的设计与变更另按 [数据库设计规范](../db-schema-guide.md) 执行；仅修改查询或持久化实现时，不要求额外加载数据库设计规范。
