# 转换为工单

将计划、规格或对话拆分为一组**工单**——曳光弹式垂直切片，每个工单都声明**阻塞**它的其他工单。

应当已经为你提供了议题跟踪器和分诊标签词汇——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

使用对话上下文中已有的内容。如果用户将引用（规格路径、议题编号或 URL）作为参数传入，则获取并完整阅读其正文和评论。

### 2. 探索代码库（可选）

如果尚未探索代码库，则进行探索以了解代码当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵守所涉及区域的 ADR。

寻找预先重构代码、使实现更容易的机会。“先让变更变得容易，再完成这个容易的变更。”

### 3. 起草垂直切片

将工作拆分成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片都以狭窄但完整的路径穿过所有层（schema、API、UI、测试）——是垂直切片，**不是**某一层的水平切片
- 每个已完成切片都能独立演示或验证
- 每个切片的规模都应适合在一个全新的上下文窗口中完成
- 任何预先重构都应首先完成

</vertical-slice-rules>

为每个工单标明其**阻塞边**——开始该工单之前必须完成的其他工单。没有阻塞项的工单可以立即开始。

**大范围重构是垂直切片的例外。****大范围重构**是一项机械式变更——重命名列、重新定义共享符号类型——其**影响半径**扩散到整个代码库，以至于一次修改会破坏成千上万个调用点，任何垂直切片都无法保持绿色。不要强行将其变成曳光弹；应按**扩展—收缩**排序。首先扩展：在旧形式旁加入新形式，确保不会破坏任何内容。然后按影响半径分批迁移调用点（按包、按目录），每一批作为一个由扩展工单阻塞的独立工单；由于旧形式仍存在，批次之间 CI 始终保持绿色。最后收缩：所有调用者都迁移后删除旧形式，该工单由所有迁移批次阻塞。如果连单独批次也无法保持绿色，则保留这个顺序，但让它们共享一个集成分支，并全部阻塞最终的集成与验证工单——只在最后的工单中承诺绿色。

### 4. 询问用户

以编号列表呈现建议的拆分。对每个工单展示：

- **标题**：简短、描述性的名称
- **被哪些工单阻塞**：必须先完成的其他工单（如有）
- **交付内容**：该工单使哪项端到端行为可用

询问用户：

- 粒度是否合适？（太粗/太细）
- 阻塞边是否正确——每个工单是否只依赖真正构成门槛的工单？
- 是否应进一步合并或拆分任何工单？

持续迭代，直到用户批准拆分方案。

### 5. 将工单发布到已配置的跟踪器

发布已批准的工单。**如何发布**取决于 `/setup-matt-pocock-skills` 配置的跟踪器——工单内容相同，只有阻塞边的形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每个工单写一个文件，按依赖顺序从 `01` 编号（阻塞项在前）。每个文件的“Blocked by”列出它依赖的编号/标题。使用下面的单工单文件模板——每个文件一个工单，绝不要写成一个合并的工单文件。
- **真实议题跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞项在前）为每个工单发布一个议题，以便其阻塞边引用真实标识符。如果平台支持，则使用原生阻塞/子议题关系；否则将每个工单的“Blocked by”设为阻塞它的议题。除非另有指示，应用 `ready-for-agent` 分诊标签——这些工单按设计即可由代理领取。

从**前沿**开始工作：阻塞项已全部完成的任意工单。对于纯线性链，这意味着从上到下。

**不要**关闭或修改任何父议题。
