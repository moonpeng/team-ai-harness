# 原型

原型是**用来回答一个问题的一次性代码**。问题决定原型的形式。

## 选择分支

确定要回答的问题——依据用户的提示、周边代码，或者在用户在线时直接询问：

- **“这个逻辑/状态模型合理吗？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单文件 HTML——包含自由操作按钮和带标签页的引导式演练——让状态机经历那些仅靠纸面很难推理的情形，并让非开发人员也能操作。
- **“它应该长什么样？”** → [UI.md](UI.md)。在单一路由上生成若干差异显著的 UI 方案，通过 URL 查询参数和底部悬浮栏切换。

两个分支会产出截然不同的制品——选错分支会让整个原型失去价值。如果问题确实含糊且联系不上用户，则默认选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明这一假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性的，并明确标注。** 将原型代码放在靠近实际使用位置的地方（紧邻它所验证的模块或页面），让上下文一目了然；但命名必须让普通读者看出它是原型，而非生产代码。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **运行方式极其简单。** UI 原型只需项目任务运行器中的一条命令即可启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示则是用户双击即可打开的单个 HTML 文件。无论哪种方式，启动时都不应需要思考。
3. **默认不持久化。** 状态保存在内存中。持久化应当是原型要*验证*的对象，而不是原型运行的依赖。如果问题明确涉及数据库，则使用临时数据库或一个明确命名为“PROTOTYPE — wipe me”的本地文件。
4. **跳过打磨。** 不写测试；除保证原型*可运行*所需之外，不做错误处理；不做抽象。目标是快速学到东西。
5. **展示状态。** 每次操作后（逻辑）或每次切换方案时（UI），打印或渲染完整的相关状态，让用户看清发生了什么变化。
6. **完成后留存。** 将任何已验证的决策吸收到真实代码中，然后把原型本身作为**一手资料**留存：提交到 main 之外的一次性分支，并在实现工单上留下指向该分支的上下文链接。同时记录答案——结论以及它解决的问题——写入工单或提交。main 分支只保留经过验证的决策。
