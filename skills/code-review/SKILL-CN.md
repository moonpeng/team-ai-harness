从用户提供的固定点到 `HEAD`，对两者之间的差异进行双轴审查：

- **规范**——代码是否符合本仓库记录的编码规范？
- **规格**——代码是否忠实实现了原始议题/规格？

两个维度由**并行子代理**分别处理，以免彼此污染上下文，之后本技能汇总它们的发现。

应当已经为你提供了议题跟踪器——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较点

用户说的任何内容都是固定点——提交 SHA、分支名、标签、`main`、`HEAD~5` 等。如果用户没有指定，则询问。

一次性记录差异命令：`git diff <fixed-point>...HEAD`（三点形式，因此比较对象是合并基点）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点能够解析（`git rev-parse <fixed-point>`），且差异非空。无效引用或空差异应在这里失败，而不是在两个并行子代理内部失败。

### 2. 确定规格来源

按以下顺序查找原始规格：

1. 提交信息中的议题引用（`#123`、`Closes #45`、GitLab `!67` 等）——使用 `docs/agents/issue-tracker.md` 中的工作流获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 如果仍未找到，询问用户规格在哪里。如果用户说没有规格，**规格**子代理将跳过并报告“没有可用规格”。

### 3. 确定规范来源

仓库中任何记录代码编写方式的内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库自身的文档外，规范轴始终包含下面的**异味基线**——一组固定的 Fowler 代码异味（《重构》第 3 章），即使仓库没有任何文档也适用。它受两条规则约束：

- **仓库规则优先。** 已记录的仓库规范始终优先；如果仓库明确认可某种会被基线标记的做法，则不要报告该异味。
- **始终属于判断。** 每种异味都是带标签的启发式判断（例如“可能存在 Feature Envy”），绝不是硬性违规；并且与这里的所有规范一样，跳过工具已经强制检查的内容。

每种异味都按“*它是什么* → *如何修复*”描述；将其与差异进行匹配：

- **Mysterious Name（神秘命名）**——函数、变量或类型的名称没有揭示其作用或所保存的内容。→ 重命名；如果无法找到诚实准确的名称，说明设计本身含糊不清。
- **Duplicated Code（重复代码）**——同一种逻辑结构出现在变更的多个代码块或文件中。→ 提取共享结构，在两处调用。
- **Feature Envy（依恋情结）**——某个方法访问另一个对象的数据多于访问自身数据。→ 将方法移动到它所依恋的数据上。
- **Data Clumps（数据泥团）**——相同的几个字段或参数总是一起出现（一个等待诞生的类型）。→ 将它们组合成一个类型，并传递该类型。
- **Primitive Obsession（基本类型偏执）**——使用基本类型或字符串表示本应拥有独立类型的领域概念。→ 为该概念创建一个小型专用类型。
- **Repeated Switches（重复的条件逻辑）**——针对同一类型的相同 `switch`/`if` 级联在变更中反复出现。→ 使用多态替代，或让两处共享同一个映射。
- **Shotgun Surgery（霰弹式修改）**——一项逻辑变更迫使差异中许多文件发生零散修改。→ 将共同变化的内容聚合到一个模块中。
- **Divergent Change（发散式变化）**——一个文件或模块因多个互不相关的原因被修改。→ 拆分，使每个模块只有一个变化原因。
- **Speculative Generality（夸夸其谈未来性）**——为规格中不存在的需求增加抽象、参数或钩子。→ 删除；内联回去，直到出现真实需求。
- **Message Chains（消息链）**——调用者不应依赖的长串 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法隐藏这段遍历。
- **Middle Man（中间人）**——类或函数主要只是继续委托。→ 移除它，直接调用真正的目标。
- **Refused Bequest（被拒绝的遗赠）**——子类或实现者忽略或覆盖了大部分继承内容。→ 放弃继承，使用组合。

### 4. 并行启动两个子代理

**规范子代理提示词**——包括：

- 完整的差异命令和提交列表。
- 第 3 步找到的规范来源文件列表，**以及第 3 步的完整异味基线**——子代理无法从其他地方获取它。
- 任务说明：“按相关文件/代码块报告：(a) 差异中所有违反已记录规范的位置，并引用该规范（文件 + 规则）；(b) 发现的任何基线异味，说明异味名称并引用对应代码块。区分硬性违规与判断性发现——违反已记录规范可以是硬性违规，但基线异味始终属于判断，并且已记录的仓库规范优先于基线。跳过工具已经强制检查的内容。控制在 400 字以内。”

**规格子代理提示词**——包括：

- 差异命令和提交列表。
- 规格的路径或已获取的内容。
- 任务说明：“报告：(a) 规格要求但缺失或仅部分实现的需求；(b) 差异中未被要求的行为（范围蔓延）；(c) 看似已实现但实现方式似乎错误的需求。每项发现都引用对应规格行。控制在 400 字以内。”

如果缺少规格，则跳过规格子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下展示两份报告，可原样呈现或仅做轻微整理。**不要**合并或重新排序发现——两个轴是有意分离的（参见“为什么使用两个轴”）。

最后用一行总结：每个轴的发现总数，以及各轴内部最严重的问题（如有）。不要跨轴选出唯一最严重的问题——那会重新排序本应分离的结果。

## 为什么使用两个轴

一项变更可能通过一个轴，却未通过另一个轴：

- 代码遵循所有规范，却实现了错误的东西 → **规范通过，规格失败。**
- 代码完全实现了议题要求，却违反项目约定 → **规格通过，规范失败。**

分开报告可以避免一个轴掩盖另一个轴的问题。
