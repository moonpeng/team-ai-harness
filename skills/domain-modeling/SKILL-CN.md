# 领域建模

在设计过程中主动构建并完善项目的领域模型。这是一项*主动*实践——质疑术语、构造边缘场景，并在术语和决策明确的那一刻将其写入术语表与决策记录。（仅仅为了使用词汇而*读取* `CONTEXT.md` 并不属于本技能——那是任何技能都能采用的一行习惯。本技能用于改变模型，而不只是使用模型。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则仓库包含多个上下文。该地图指向每个上下文的所在位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件——只有真正有内容可写时才创建。如果不存在 `CONTEXT.md`，在第一个术语得到明确时创建；如果不存在 `docs/adr/`，在需要第一份 ADR 时创建。

## 会话期间

### 对照术语表提出质疑

当用户使用的术语与 `CONTEXT.md` 中已有语言冲突时，立即指出。“你的术语表将‘cancellation’定义为 X，但你现在似乎指的是 Y——究竟是哪一个？”

### 明确模糊语言

当用户使用含糊或多义的术语时，提出精确的规范术语。“你说的是‘account’——你指 Customer 还是 User？它们是不同的概念。”

### 讨论具体场景

讨论领域关系时，使用具体场景进行压力测试。构造能够探查边缘情况的场景，迫使用户精确定义概念之间的边界。

### 与代码交叉核对

当用户说明某项机制如何工作时，检查代码是否一致。如果发现矛盾，明确指出：“你的代码会取消整个 Order，但你刚才说可以部分取消——哪一个才是正确的？”

### 即时更新 CONTEXT.md

术语一旦明确，就立即更新 `CONTEXT.md`。不要批量积攒——在术语形成时就记录。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应完全不包含实现细节。不要将 `CONTEXT.md` 当作规格、草稿纸或实现决策的存储库。它只是术语表，仅此而已。

### 谨慎建议 ADR

只有以下三项全部满足时，才建议创建 ADR：

1. **难以逆转**——以后改变主意的成本很高
2. **缺少上下文时令人意外**——未来读者会疑惑“为什么要这样做？”
3. **真实权衡的结果**——存在真正的替代方案，并出于明确原因选择了其中一个

缺少任何一项都应跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
