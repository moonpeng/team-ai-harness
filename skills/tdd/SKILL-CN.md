# 测试驱动开发

TDD 是红 → 绿循环。本技能是确保该循环产出值得保留的测试的参考：什么是好测试、测试应放在哪里、反模式，以及循环规则。每一节都适用于每一轮循环——应在循环之前和过程中查阅，而不是结束后才看。

探索代码库时，读取 `CONTEXT.md`（如果存在），使测试名称和接口词汇符合项目的领域语言，并遵守所涉及区域的 ADR。

## 什么是好测试

测试应通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，测试不应随之失效。好测试读起来像规格说明——“用户可以使用有效购物车完成结账”准确说明了存在什么能力——并且不关心内部结构，因此能经受重构。

示例参见 [tests.md](tests.md)，模拟指南参见 [mocking.md](mocking.md)。

## 接缝——测试放在哪里

**接缝**是进行测试的公共边界：你可以在这里观察行为，而不必探入内部。测试位于接缝处，绝不针对内部实现。

**只在事先约定的接缝处测试。** 编写任何测试之前，先写明要测试的接缝并与用户确认。不得在未经确认的接缝处编写测试。你无法测试一切——提前约定接缝，才能让测试投入落在关键路径和复杂逻辑上，而不是每一个边缘情况。

询问：“公共接口是什么？我们应该测试哪些接缝？”

如果接口本身的形态仍有疑问——模块应有多深、接缝应在哪里、接口应暴露什么——使用 `/codebase-design` 技能提供的术语。它是模块、接口、深度、接缝、适配器、杠杆率和局部性等术语的共同来源；它是供查阅的参考，而不是要运行的会话。

## 反模式

- **与实现耦合**——模拟内部协作者、测试私有方法，或通过旁路验证（例如不使用接口而直接查询数据库）。识别信号：行为没有变化，仅重构就导致测试失败。
- **同义反复**——断言以与代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、用相同方式手工推导快照、断言常量等于自身），因此测试按构造必然通过，永远不可能与代码产生分歧。期望值必须来自独立的事实来源——已知正确的字面值、推导完成的示例或规格说明。
- **水平切片**——先写完所有测试，再写所有实现。批量测试验证的是*想象中的*行为：你测试的是事物的*形状*而非面向用户的行为；测试对真实变化不敏感；并且在理解实现之前就锁定了测试结构。应改为使用**垂直切片**——一个测试 → 一个实现 → 重复；每个测试都是一颗**曳光弹**，并根据上一轮循环学到的内容作出响应。

## 循环规则

- **先红后绿。** 先写会失败的测试，再只编写足以让它通过的代码。不要预判未来测试，也不要增加推测性的功能。
- **每次一个切片。** 每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于这个循环。** 重构属于审查阶段（参见 `code-review` 技能），而不是红 → 绿的实现循环。
